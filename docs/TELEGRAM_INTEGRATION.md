# Telegram control plane

## Preflight review (2026-11-06, before implementation)

Baseline local and remote were verified as `f87c6c35d4da70cfe8ef36d7ada722c149cdd07f`; the tree was clean and `feat/v2-p3-telegram-control` was created with approved Git execution, without ACL changes.

Source review: P2 agent credentials are separate from browser authentication; fixed task kinds, session/attempt/lease fencing, dependency claims and immutable checkpoints already exist. UsageApi reads sanitized PostgreSQL quota snapshots and computes freshness; Telegram must reuse it without inference or collector calls. TaskCycles currently derives RUNNING/FAILED/SUCCEEDED from tasks, has no persisted cycle state or pause/resume/cancel API. AgentQueue claims do not check cycle state. Task events commit transactionally, but there is no outbound dispatcher, durable Telegram offset, routing registry or approval engine. These are the P3 gaps; P2 is preserved.

The [official Bot API](https://core.telegram.org/bots/api) makes getUpdates and webhooks mutually exclusive. Poll offsets acknowledge earlier updates and must follow committed processing. The [official bot-to-bot documentation](https://core.telegram.org/bots/features#bot-to-bot-communication) now describes optional BotFather configuration. P3 does not assume it is enabled: bots coordinate internally through PostgreSQL, incoming bot messages are ignored, and Executor/Reviewer remain future routing roles rather than implemented AI coding.

## Implemented contracts

V13 adds persisted cycle state/events, bot identities, registered routes, numeric operator allowlists, sanitized update receipts, fixture approvals and outbox. V14 adds a durable per-chat send budget. Tokens are resolved on the backend host from the registered environment key (default name `TELEGRAM_BOT_TOKEN`); PostgreSQL stores the key name only. Neither frontend nor API accepts a token value. HTTP errors are fixed codes; token-bearing transport URLs and raw Telegram errors are never logged or persisted. Incoming message text is not stored.

`TELEGRAM_ENABLED` defaults to false. No webhook endpoint or public inbound port is added. A dedicated bounded worker pool prevents long polling from blocking agent recovery scheduling. Pollers acquire a PostgreSQL per-bot lease, verify getMe's numeric bot ID and require an empty getWebhookInfo URL before polling. They do not delete webhooks. A batch of at most 100 updates is validated/sorted, receipts deduplicated by bot/update ID, fixed commands processed and reply outbox rows committed before the next offset is stored. Failure rolls back processing and offset. An unseen ID below an already committed offset is recorded OLD_UPDATE without replaying an action.

The registered chat AND numeric user must match. READER can issue read commands; OPERATOR/ADMIN additionally require the route's control/approval flag. CODE alone permits cycle controls. Omitted operators become REVOKED, preserving audit foreign keys while removing read/control authority. Incoming bots and anonymous sender_chat identities are ignored; reply depth is bounded to three. One command per second per user/chat bounds responses. Unsupported text is never echoed. Explicit `/command@botname` mentions are currently ignored; use the listed unqualified commands. BotFather bot-to-bot configuration is not inferred or enabled by CreatorFlow.

Commands: `/help`, `/status`, `/agents`, `/tasks`, `/cycle <uuid>`, `/usage`, `/pause <uuid>`, `/resume <uuid>`, `/cancel <uuid>`, `/approvals`, `/approve <uuid>`, `/reject <uuid>`. Lists are bounded to ten items. `/usage` calls the existing database reader only: 300/10080-minute windows, remaining/used percentages, UTC reset timestamp, last sync/source/agent, computed freshness and warnings; no inference, refresh or quota collection. Sensitive task results, prompts, credentials and provider responses are excluded.

Cycle state is durable: QUEUED/RUNNING/PAUSED/CANCEL_REQUESTED/CANCELLED/SUCCEEDED/FAILED. Controls lock agent -> cycle -> tasks to serialize against claims. PAUSED forbids new claims while active tasks continue. Resume accepts PAUSED and leaves dependency/capability/backoff checks in the existing claim path. Cancel cancels pending nodes and requests fenced cancellation for active nodes; completion/recovery settles CANCELLED, never requeues a cancelled cycle. Terminal transitions reconcile from committed task state. Repeated pause/cancel and duplicate Telegram updates are safe; resume requires PAUSED. Existing handoff generation/checkpoints remain intact.

Approval is limited by database constraints to FIXTURE_CYCLE/FIXTURE_REVIEW. It binds a persisted cycle/evidence UUID, bot/chat, assigned numeric operator, expiration and terminal decision. Callback data `approve:<uuid>` or `reject:<uuid>` passes the same binding/authority/expiry/state checks as commands. Duplicate/opposite/stale decisions cannot overwrite a terminal decision. The decision commits with its reply outbox; no publishing or shell action is dispatched. There is no inline keyboard in P3; commands work and callback validation supports a future keyboard.

Task and cycle event triggers create CODE notifications inside the producer transaction. Allowlisted activity event types route content/script/storyboard to CONTENT and asset/render/publication status to VIDEO; only event/entity IDs and fixed event types are copied. No activity message/metadata or prompt is forwarded. Each outbox row has a unique event/route key and persisted reference. Poll command replies and approval requests also enter the same outbox transactionally.

Outbound delivery claims are durable and serialized: one attempt/second/bot and one/three seconds/chat, no redirects, 25-second request deadline, maximum five known rejected attempts with capped backoff and Telegram retry_after. Known 429 rejection retries; definitive errors or exhausted attempts enter DEAD_LETTER. Timeout, 5xx, invalid send confirmation or expired SENDING after a crash enters UNKNOWN quarantine, because a remote send may already exist. UNKNOWN is never automatically resent. This is an at-least-once retry design with explicit uncertain-result reconciliation, **not exactly-once delivery**. An operator must inspect the referenced chat/event before any future manual reconciliation; no blind resend button is provided.

## Local operator API and setup

All paths require the existing browser/operator bearer credential. Agent credentials are denied. No Telegram public inbound API exists.

- `GET /api/v2/telegram`: sanitized status, bot availability/poll/send timestamps, registered mappings/operators, outbox summary and bounded errors. Never returns tokens or their environment keys.
- `POST /api/v2/telegram/bots`: `{identity,botId,tokenEnv}`. Identity and numeric bot ID/environment reference are immutable; register another identity instead of silently repointing it.
- `PUT /api/v2/telegram/routes`: `{botIdentity,chatId,kind,canControl,canApprove,operators:[{userId,role}]}`. Register exact IDs; usernames cannot be used. Roles are READER/OPERATOR/ADMIN. Revoking an identity requires omitting it from the replacement list; retained audit rows show REVOKED.
- `POST /api/v2/telegram/routing-test`: validates persisted mappings; returns `delivery: NOT_SENT` and does not contact Telegram.
- `GET/POST /api/v2/telegram/approvals`: list or create `{cycleId,botIdentity,chatId,requiredOperator,expiresMinutes}` (1–60 minutes). No real publication action exists.
- `POST /api/v2/task-cycles/{id}/pause|resume|cancel`: same durable cycle control for the authenticated local operator.

Configure the token outside Git on the backend host, register verified numeric bot/chat/user metadata, and verify webhook removal through the official operator-owned BotFather/API flow before opting into polling. Keep the backend bound to loopback. Register each intended bot separately, with its own environment reference. Do not enable polling or attempt a live send as part of fixture acceptance. This cycle has no configured live token/chat and no live send authorization.

The `/telegram` sidebar page reuses existing components and reads actual backend data: disabled/config state, bot availability, all three route kinds, operator metadata, send errors/quarantine and fixture approval queue. Routing validation deliberately sends nothing. No demo success fallback exists in real mode.

## P4/P5 dependency proposal

1. P4: controlled content pipeline with artifact/evidence manifests and durable approval binding to immutable action inputs. Test official provider adapters, scopes, expiry/replay and unknown-result reconciliation using mocks first. Live publishing remains a separately authorized acceptance step; P3 fixture approval cannot grant it.
2. P5 foundation: credential lifecycle/rotation and retention; per-repository isolated worktrees, one writer, validated task schema, Windows process-tree deadlines, allowed repository/branch boundaries, checkpoint integrity and secret-safe evidence.
3. P5 execution: verify installed official Codex/Gemini execution capabilities, introduce explicit AI task kinds and quota admission before scheduling/claim. Fresh READY data plus configured budget/operator authorization is required; WAIT_FOR_RESET waits, UNKNOWN/STALE/unsupported quota requires an operator decision. Git/FFmpeg fixtures stay quota-independent. Never switch accounts to evade limits.
4. P5 review: Planner -> isolated Executor -> Reviewer/tests -> operator-reviewed draft PR; no automatic merge or deploy. Durable cancellation/restart must retain worktree/evidence ownership. Telegram roles are routing until these executors pass acceptance. Any periodic/five-hour trigger is a later opt-in task after overlap/quota/approval tests; none is created here.
