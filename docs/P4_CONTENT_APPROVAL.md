## P4-01 immutable manifests and provenance

V15 adds `publication_manifests`, `artifact_evidence`, publication audit, approval storage and job binding fields. V16 constrains approval transitions and immutable bindings. Manifest/evidence/audit UPDATE and DELETE are rejected by PostgreSQL triggers. Schema 1 canonical serialization recursively sorts object keys, preserves array order and explicit values, uses compact UTF-8 JSON and SHA-256. Only integral media sizes/durations/revision numbers are used; timestamps are explicit UTC strings. UUID, immutable creation time and revision are part of the fingerprint input; the fingerprint itself is not recursively hashed. A revision is a new record, never an overwrite.

Creation locks the publication and requires the current successful render linked to the exact FINAL_VIDEO asset/content, one persisted storyboard with ready source assets, actual voice provenance and any subtitle references. Files must resolve inside the configured media root, be regular/non-symlink, within 250 MiB, with DB sizes matching. Existing media validation decodes video and source audio/images/subtitles; bounded ffprobe records duration/container/codec evidence. Before/after SHA checks reject bytes changing during validation. The manifest stores IDs, checksums, byte sizes and evidence, never storage paths, provider responses, tokens, OAuth caches or storyboard prompts.

The immutable payload binds content/storyboard version, final render/video, media SHA/size/duration/container/codecs, exact title/caption/description/hashtags/provider description, platform, exact connection ID **and connection revision**, explicit visibility, intended schedule, creation time, evidence and source artifact references. Fixed provider options (category 22, made-for-kids false, notify-subscribers false) are explicitly recorded/displayed. The YouTube description is the recorded description, caption and hashtag text separated by blank lines; tags are sent from the exact hashtag array. Source files, storyboard version and current render are checked again before dispatch.

`social_connections.connection_revision` rotates whenever encrypted credential, scope, status or revocation changes. Reconnecting a different account into the existing one-connection-per-platform row cannot inherit a previous approval. This remains local connection identity metadata, not a new live channel-ownership attestation; no account lookup/login/switch is performed in P4.

## P4-02 exact operator approval

Publication approval is separate from P3 fixture approval. Each manifest creates a PENDING request assigned to the authenticated existing `local-user` operator, issued with a one-hour review deadline. An APPROVE/REJECT decision requires the exact active manifest/fingerprint, assigned operator and a UUID idempotency key. Approval also verifies current metadata, connection revision, sources and final bytes. Decision expiry can only shorten, capped at the original deadline; UI approval uses up to 30 minutes. Same key + same decision returns the committed decision; another key, opposite decision or cross-manifest replay is rejected. Revocation, expiry and invalidation cannot be reversed into approval; create a fresh revision.

DB triggers freeze approval identity/fingerprint/operator/issuance and committed decision fields, constrain terminal transitions and prohibit extending expiry. Audit is append-only. Metadata/platform/account/visibility/schedule changes atomically invalidate the active approval and clear the active manifest. An in-flight/published/unknown target cannot be silently edited. Render/asset/source-byte changes are caught by guard validation even if the metadata API was not used.

The existing local bearer remains a single operator identity; no multi-user RBAC claim is made. Agent credentials cannot read/write review APIs. Telegram numeric permissions remain confined to P3 fixture decisions: even a fixture APPROVED row with a matching UUID cannot satisfy `publication_approvals`. Historical approved_at is retained as history but is never migrated into a P4 approval. The legacy approve endpoint returns 409 IMMUTABLE_MANIFEST_APPROVAL_REQUIRED.

## P4-03 universal gate and provider dispatch

`PublicationSafety` owns all uploads. Manual publish and the existing scheduler delegate to it; retry validates the same binding before requeue, and the eventual dispatch validates again. Recovery never uploads an unknown attempt. The adapter accepts only a private-constructor guard-issued permit, not a raw file path/title. Source review after implementation found one call to `youtube.publish`, inside this owner.

The production gate first checks CREATORFLOW_ENABLE_REAL_PUBLISH, then persisted manifest integrity/target/metadata, exact connection revision/status/credential presence/upload scope, adapter configuration, unexpired operator approval, explicit supported visibility, current render/storyboard/source evidence, actual video checksum and reconciliation/target state. Claims lock the job and atomically persist PUBLISHING, increment the attempt and issue a dispatch token before provider I/O. Canonical target uniqueness from P0 is preserved. Metadata edits/revisions cannot replace a claimed/published target. Manual dispatch also respects the approved intended schedule; an early upload requires a newly reviewed schedule revision. Failed jobs need validated retry, not another direct claim.

Capture copies a bounded exact-size snapshot to a private staging file, verifies its SHA and holds an OS file lock/open handle through transfer. The upload body reads that handle, never reopens a mutable asset path. The permit rechecks DB/approval/account/source bytes before OAuth use, after token refresh and immediately before video PUT, including replacement/revocation during resumable initialization. A later source overwrite cannot substitute different upload bytes. Staging uses delete-on-close. This is a linearized dispatch authorization, not a promise to undo bytes already in flight if an operator revokes after transfer has started.

YouTube uses the exact connection/revision to refresh its approved encrypted credential; it no longer chooses a generic account. Scope matching is exact. Visibility comes only from the manifest; confirmation requires the exact returned post ID, processed state and approved visibility. Redirects and foreign resumable upload origins are not accepted. No silent fallback to public/private occurs.

Production construction remains LIVE; changing configured endpoint URLs to loopback cannot bypass the real-publish flag. Tests explicitly construct the duration-injected adapter on loopback only, classified MOCK_ONLY; that adapter capability is not an HTTP parameter or a runtime mode toggle. All acceptance has CREATORFLOW_ENABLE_REAL_PUBLISH=false and TELEGRAM_ENABLED=false. Fixture tokens are provided by test overrides; no real provider credentials are used. Other social adapters remain NOT_CONFIGURED.

## P4-04 recovery and unknown outcomes

Rejected initialization or timeout before video transfer is PRE_UPLOAD_FAILURE/FAILED and can retry only through the same guard. Once PUT may have begun, timeout, malformed/missing ID or rejected/ambiguous response quarantines PUBLISHING with UPLOAD_OUTCOME_UNKNOWN and reconciliation_required=true. Manual, scheduled, retry and new-revision paths cannot blindly resend. Startup also quarantines PUBLISHING without a post ID.

A returned post ID is committed before confirmation. Confirmation can recover a known ID without uploading again; a wrong ID or visibility stays PUBLISHING/CONFIRMATION_PENDING, never PUBLISHED. Confirmation transport failure persists CONFIRMATION_ERROR. A revoked/expired/changed approval or account still blocks confirmation under the current conservative policy. An operator must review these stuck/unknown cases; P4 supplies audit/status but no arbitrary post-ID attach, quarantine-clear or blind resend API. A future reconciliation workflow needs separately reviewed evidence/authority contracts. Database loss immediately after provider success remains an uncertain result, quarantined at startup rather than retried.

## P4-05 frontend and operator APIs

Existing routes/layout are retained. Publication Queue now links to `/publication-jobs/:id/review` and does not auto-approve before publishing. Review uses actual backend data and checksum-verified authenticated video preview, immutable revision/history, exact metadata/account/visibility, render/codec/evidence checksums, previous-approved revision changes, readiness/reconciliation and audit. Explicit visibility is required. Create, approve/reject, revoke and invalidate are separate controls. Dirty fields or a preview checksum mismatch disable approval. A disabled/unconfigured provider cannot appear as a successful Publish action; the result is only called confirmed when PUBLISHED with a real adapter-returned post ID. Real mode has no mock success fallback.

Authenticated local operator APIs:

- `GET /api/v2/publication-review/jobs/{id}`: immutable history, current manifest, readiness, sanitized connection/render references and audit.
- `POST /api/v2/publication-review/jobs/{id}/manifests`: `{renderJobId,connectionId,visibility}`; captures the job's current exact metadata into a new revision.
- `GET /api/v2/publication-review/manifests/{id}`: exact payload/fingerprint and effective approval state.
- `POST /api/v2/publication-review/manifests/{id}/decision`: `{fingerprint,decision:APPROVE|REJECT,requestId,expiresMinutes:1..60}`.
- `POST /api/v2/publication-review/manifests/{id}/revoke` and `/jobs/{id}/invalidate`: revoke or invalidate without deleting history.
- Existing `/api/publication-jobs/{id}/details` additionally accepts description/connectionId/visibility, with transactional invalidation. Existing publish-now/retry/scheduler all use the guard. Legacy `/approve` fails closed.
